Biome CLI 2.6.6 adds 12 new nursery lint rules and faster linting

6 November 2026

Biome, which is a fast code formatter and linter for JavaScript and TypeScript, released version 2.6.6. The release adds twelve new nursery rules. A nursery rule is a new rule that is still being tested, so you must turn it on yourself. Many of the new rules catch code that breaks at run time. For example, noArrayMethodsOnArguments catches calls like arguments.reduce(), which throw a TypeError because arguments is not a real array. noNumberArgumentOutOfRange catches calls like value.toString(64), which throw a RangeError. Other rules catch pointless code, such as price * 0 in noErasingOperation, or a condition that can never be true in noConstantComparisons. There is also noSvelteIgnoredUnsubscribe, which finds Svelte store subscriptions you never stop, a common memory leak. For daily work, these rules move whole classes of silly bugs from run time to the moment you save the file. The release also makes linting faster, because each pass now skips syntax nodes that no enabled rule looks at, and it fixes a bug where rule groups with more than 256 rules could turn on the wrong rule. Since all twelve rules sit in the nursery, expect some of them to be promoted to stable groups in later Biome releases.

Docker explains when to use Docker Sandboxes instead of containers for AI agents

6 November 2026

Docker published a guide that explains the difference between a container and a Docker Sandbox. A container is just an isolated process, and it shares the Linux kernel with the host machine, which is why containers start fast and use few resources. Docker Sandboxes are different. Each sandbox is a microVM, which is a very small virtual machine with its own Linux kernel, its own filesystem, its own network, and its own private Docker Engine. Inside a sandbox, an AI coding agent gets sudo rights, so it can install packages, start a database like PostgreSQL, and build images without touching your real machine. You start one with a single command using the sbx command line tool, for example sbx run claude. This matters because a coding agent works for hours and keeps state, and it also reads instructions from README files, web pages and tool output that nobody checked. Docker's advice is simple: sandbox the agent, and containerize the application the agent works on. Containers stay the right choice for packaged apps, continuous integration jobs and short tasks.

Thoughtworks explains context rot, when an AI agent stops using its own context well

5 November 2026

Thoughtworks published a guide about context rot. Context rot is when an AI agent gets worse at using the information it holds, because that information grows too big, too old or too noisy. The guide follows a real case. A coding agent started with a small bug fix, read the code, changed it and ran the tests. Then the task grew with more files, logs, test failures and old attempts. The agent began to retry failed ideas, forget earlier rules and work on details that no longer mattered. The guide names five causes: long conversation history, noisy tool output, outdated or conflicting notes, loading too much at the start, and the limit of the context window, which is the amount of text a model can read in one go. A 2025 test by Chroma on 18 large language models (LLMs) found that results drop as the context gets longer. The practical lesson is to keep only what the agent needs for its next step, feed details in when needed, and check the context the agent had before a bad decision. Thoughtworks also separates context rot from context poisoning, where a bad or hostile instruction enters the context from an untrusted file.

OpenAI engineer Predrag Gruevski shares his AI workflow for writing correct Rust code

5 November 2026

Predrag Gruevski works on frontier systems at OpenAI and built cargo-semver-checks, a tool that catches breaking changes in Rust libraries before they ship. On a JetBrains RustRover livestream, he explained his way of working with AI coding agents. The first step is sorting the work by risk before he writes any prompt. Low-stakes code, like a GitHub Actions file that runs tests automatically, goes straight to the agent. Code other people depend on gets much more care, so he asked AI to invent fake breaking changes to hunt for false alarms. Unsafe Rust code, where a bug can corrupt data, he still reads line by line, and he says four hours for 100 lines is a fair price. The second step is the prompt itself. He sketches the design, the types and the test structure, says which assumptions are fine to make, and sets the quality bar. For one task he spent 45 minutes writing a single prompt for Codex, telling it to look at hot compiler code nobody had tuned lately, prefer small changes, and only accept at least a 1% speedup measured in interleaved benchmark runs. The result was one deleted line in Rust's new trait solver that made it up to 7.5% faster. The third step is review, and he now checks the design and the tests instead of every line. If you write code where mistakes are expensive, this gives you a concrete way to spend your attention: let the agent handle the cheap parts and move your hours to the 20 lines that can really hurt you. JetBrains runs the series with the Rust Foundation, and the full livestream recording is on the JetBrains blog.

Go 1.27 ships encoding/json/v2, a new stable JSON library for Go

5 November 2026

The Go team has made two new packages stable and available in Go 1.27: encoding/json/v2 and encoding/json/jsontext. JSON, which means JavaScript Object Notation, is a simple text format used to send data between programs. Go has had the encoding/json package since before Go 1.0, more than fifteen years ago. The old package has problems that cannot be fixed without breaking existing code. It accepts invalid UTF-8 text, so bad data can pass through quietly. It accepts objects with duplicate names, which attackers have abused before, as in the security bug CVE-2017-12635. It matches JSON names to Go struct fields without caring about upper or lower case, which is slow and surprising. It also turns an empty slice or map into null instead of an empty list or object. The new version fixes all of these, lets you pass options down to your own MarshalJSON and UnmarshalJSON methods, and adds real streaming so large values are not held fully in memory. If you write Go services that read or write JSON, you get stricter safety checks and better speed, but you must read the new default behaviour carefully, because your output can change. The old encoding/json package stays, so you can move over one package at a time.

Hugging Face proposes Model Integration Contracts to catch Transformers bugs on every PR

3 November 2026

Hugging Face has published a proposed standard called transformers-mic, short for Model Integration Contracts. A Model Integration Contract has three parts. First, a fixture, which is a tiny copy of a real model, built from the real model's settings but with fewer and narrower layers. Second, a usage path, which is a runnable example such as generating text or running one training step. Third, baselines, which are the recorded outputs a human has checked. The contract holds if running the example on the tiny model still gives the same outputs. The reason for this work is a real bug. On July 30, 2026, Transformers turned on PyTorch's scaled dot-product attention (SDPA) for the T5 model, and this let UMT5's decoder look at future tokens during training. Nothing crashed, and the bug stayed in the main branch until September 28. Transformers supports over 750 model types and runs more than 88,000 processor tests plus over 200,000 graphics card tests, so the full suite cannot run on every change. The tiny UMT5 fixture used only 66 MB of weights instead of 1,227 MB, and a replay over five months of commits flagged the bug every single time, with label log-probabilities off by 1.22 and training loss off by about 0.20. For you, this means model bugs can be caught in a pull request instead of weeks later, and on a cheap processor runner the T5 contract took just 13.4 seconds. One lesson is worth copying: the contract only caught the bug because it used SDPA, the default attention path, so your small test models must run the same code path as the real ones. The standard is still a proposal, and the contracts are published in a Hub collection named huggingface-mic.

Allen Institute for AI releases StateBench to test how models track changing facts

4 November 2026

The Allen Institute for AI released StateBench, a benchmark, which is a standard test used to compare models against each other. StateBench checks how well a language model keeps track of facts that change across a very long document. The test has four levels. At the easiest level, called r-trivial, a value is set once and never changes, like let x = 4. The next level, aperiodic, allows a value to be replaced, so the model only needs the newest one. The third level, soluble, uses updates that build on the old value, like x = x + 5. The hardest level, general finite, lets one variable copy another, like x = y or swapping two variables. The team tested Olmo 3, a 7-billion-parameter transformer, against Olmo Hybrid, which adds Gated DeltaNet layers that carry a running memory forward. The hybrid and recurrent models handled long inputs far better. Frontier models such as Gemini 3.8 Flash, Claude Opus 5.5, GPT-6 Sol and GPT-6 Luna still failed on the hard levels as inputs grew. If you use a model to read long code or long logs, this tells you where it will silently lose the thread, and reassignment chains are the risky part. The tech report, the data and the code are all public.

Docker wrote a guide for Docker Sandboxes, which are safe boxes where an AI coding agent can run commands without touching your computer. The command line tool is called sbx. The guide shows three setups, and all of them help the part of the work where code gets written and reviewed. First, you run sbx run from your project folder, and Docker mounts that same folder inside the sandbox, so you and the agent edit the same files and your dev server reloads as normal. Second, you give each task its own Git worktree, which is a separate folder and branch from the same repository, but Git commands like git status must then run on your computer, not in the sandbox. Third, clone mode mounts your code as read-only and makes the agent its own clone with Git inside, so you pull its branch back later. A sandbox with no mount at all works like a remote machine: you open a shell with sbx exec, and you publish a port, such as 8080, to see the app in your browser. The useful part is control. Pick the shared folder when you work next to the agent, and pick clone or no-mount when you want the agent to run several tasks alone. One warning matters: deleting a sandbox deletes files that live only there, so push your branch first.

Google and Meta open-source TorchTPU for native PyTorch on Google TPUs

3 November 2026

Google and Meta have released TorchTPU as an open-source project. TorchTPU is a native backend for PyTorch, which is a popular open-source library for building and training machine learning models. The backend lets PyTorch code run directly on Google TPUs, which are Google's own chips built for machine learning work. Before TorchTPU, using PyTorch on TPUs needed extra layers and extra effort. With TorchTPU, you only need very small changes to your code. TorchTPU supports eager execution, where each operation runs right away, and compiled execution, where the code is turned into a faster optimised program first. TorchTPU also supports distributed computing, which means spreading one training job across many chips, plus optimisations made for the TPU hardware itself. For a PyTorch team, TPUs now become a real option next to GPUs, without rewriting the training code.

Google reveals PageBreak, an AI security agent that found over 500 XSS bugs

31 October 2026

Google published a paper about PageBreak, an AI security agent that hunts for bugs in Google's own web applications. PageBreak has found more than 500 XSS bugs since it started full operation in January. XSS means cross-site scripting, a bug where an attacker can inject their own code into a web page that other people visit. The way of working has two clear steps. First, Gemini models look at a web application on their own and guess where a weak spot might be. Second, deterministic validators, which are fixed test programs that always behave the same way, try to run the real attack against a live, running application. PageBreak only files a bug report when that second step succeeds. So this way of working belongs to the review and testing part of building software, and it shows a useful pattern for your own tools: let the model explore and guess, then let plain code prove the guess is real before any human reads it. That order removes the biggest problem with AI bug hunting, which is a long list of false alarms that waste engineer time.
