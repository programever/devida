Bun v1.4.3 adds bun check, a built-in TypeScript type checker up to 6.4x faster than tsc

10 October 2026

Bun v1.4.3 is out, and it fixes 166 issues. The biggest new thing is bun check, a TypeScript type checker built into Bun. A type checker reads your code and tells you when you use the wrong kind of value, for example a text value where a number is needed. bun check passes 100% of the conformance test suite of TypeScript 7.0.2, which is the official set of tests that proves a checker behaves correctly. On a 16-core Apple silicon Mac it runs 3x to 6.4x faster than tsc 7.0.2 and uses 2.2x to 4.9x less memory. It is a port of typescript-go, it reads your tsconfig.json file, and you do not need the typescript package installed. You can now add --check to bun run, bun test and bun build, so a type error stops your code, your tests or your bundle before they go further. The release also cuts idle server CPU use by 67 to 89%, makes large node:http responses up to 2.7x faster, and adds Bun.FetchSession for per-group network settings. Bun.ModuleGraph, which runs many copies of one app in one process, is still marked experimental. bun check only checks types, so your editor keeps using the normal TypeScript language server.

Facebook releases Lifeguard, a static analyzer for Python Lazy Imports

10 October 2026

Facebook has released Lifeguard, a tool that checks if your Python code is ready for Lazy Imports. Lazy Imports is a new feature from PEP 810, a Python design document, that waits to load a module until you first use a name from it. Lazy Imports can cut memory use and startup time, which helps a lot in big codebases. But some code breaks when imports are delayed, for example a module that registers itself in a global dictionary at import time, or code that reads sys.modules. Lifeguard reads your source files in parallel and walks the abstract syntax tree, which is the parsed structure of your code, to find these unsafe patterns. Lifeguard is conservative, so it marks a module unsafe when it cannot prove the module is safe. You install it with pip install lifeguard-lazy-imports, and it needs Python 3.12 or newer. The team wants Lifeguard ready for general use by the final release of Python 3.15, and a standalone linter mode that points at exact lines is still being built.

Culpert, a Rust heap profiler that links allocations to spans, reaches version 0.2.1

10 October 2026

Culpert is a new open source tool for Rust. It is a heap profiler, which is a tool that measures how much memory a program asks for while it runs. The new part is that Culpert links each memory allocation to a span, which is a named section of code that tracing tools already mark. So instead of only seeing that a function allocated memory, you see which request or step did it. Culpert works with tracing, with Cloudflare Foundations, or with its own span_fn macro, and version 0.2.1 is on crates.io now. It writes profiles in the pprof format, so existing tools like pprof, Speedscope, Pyroscope and Polar Signals still work. It also ships a command line tool with a diff command for continuous integration, so a pull request can fail when memory use grows. Cloudflare already caught real allocation problems with it, including a memory leak, before release. The authors still mark Culpert as very experimental, so avoid production for now.

5 October 2026

Iroh, a Rust networking library for direct peer-to-peer connections, has published its plan for global content discovery, which means finding out who on the internet has a piece of data you want. The team looked at existing systems and picked BitTorrent as the model, because it has worked for over two decades. BitTorrent launched in 2001 with central trackers, then added a distributed hash table (DHT) called Mainline in 2005. A DHT is a shared lookup table spread across many computers, with no central server. Iroh now reuses Mainline to announce and find providers for its own blobs. Instead of BitTorrent's SHA-1 piece hashes, iroh-blobs uses BLAKE3 verified streaming, so a single root hash is enough to check any part of a large file. The timing matters because IPFS Shipyard is shutting down, and many developers used IPFS for exactly this job. Mainline lookups often finish in well under a second, and one real test returned a result in 37 milliseconds. Efficient multi-provider downloads of a single blob are still unfinished work.

pg_ivm 1.16 adds PostgreSQL 19 support and fixes four view maintenance bugs

5 October 2026

The IVM Development Group released pg_ivm 1.16, an extension for PostgreSQL that provides Incremental View Maintenance (IVM), which is a way to keep a materialized view up to date by computing only the changes instead of rebuilding the whole view. The new version adds support for PostgreSQL 19 and fixes four bugs. One bug caused a segfault, which is a hard crash of the database process, when an incrementally maintained materialized view (IMMV) was maintained and dropped in the same transaction. Another bug broke view maintenance when a base table held a column type with no default equality operator, even when the view did not use that column. A third bug broke maintenance once the global object identifier (OID) counter passed INT_MAX. The fourth fix stops transactions from failing with a lock error when no concurrent maintenance was actually running. If you use pg_ivm to keep reporting views fresh, these fixes remove crashes and random failures that were hard to reproduce, and the PostgreSQL 19 support means you can upgrade the server without dropping the extension. The source code lives in the sraoss pg_ivm repository on GitHub.
